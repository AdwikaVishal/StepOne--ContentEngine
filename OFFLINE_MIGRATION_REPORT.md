# Content Engine — Complete Offline AI Migration (Local Qwen Only)

## Status: COMPLETE

Every language-generation pathway in Content Engine now routes exclusively through the
downloaded local Qwen2.5-1.5B-Instruct model (`models/qwen/`) via PyTorch + transformers.
Groq, Gemini and OpenAI inference are unreachable — no code path can instantiate or call them.

---

## 1. Root cause of Groq being selected

- `content_engine/providers/factory.py::get_llm_provider()` returned `GroqProvider()` whenever
  `AI_EXECUTION_MODE=cloud_testing`, and `get_vision_provider()` returned `GroqVisionProvider()`.
- `content_engine/brand/brand_matcher.py` instantiated `Groq(api_key=settings.groq_api_key)`
  directly for `_llm_verify()` logo verification (independent of the factory).
- `content_engine/captioning/providers/groq_provider.py` contained a Groq caption adapter
  (importable, though not wired to the default factory).
- `content_engine/copy_generator.py` contained a `_GroqGenerator` class (`Groq()` +
  `client.chat.completions.create`) — dead code, never instantiated (`CopyGenerator._groq is None`).
- `.env` contained real `GROQ_API_KEY` and `GEMINI_API_KEY` values.
- Frontend `ResultsPage.tsx` displayed backend `'groq'` as `"Groq (llama-3.3-70b)"`.

The local provider was not being "bypassed" in the default `local` mode — captions already went
through Qwen via `CopyGenerator → get_llm_provider() → TorchLocalProvider`. The Groq exposure came
from (a) the optional `cloud_testing` mode in the factory, (b) the direct Groq client in
`brand_matcher.py`, (c) dead-but-present Groq code, and (d) frontend labels.

## 7. Offline / network-isolation evidence

- Enforced in code at import time (before transformers): `HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1`, `HF_HUB_DISABLE_TELEMETRY=1`, `TORCH_LLM_LOCAL_FILES_ONLY=true` (also present in `.env`).
- `get_torch_status()` reports `offline_enforcement` all four vars set, `local_only: true`, `remote_inference_disabled: true`.
- Missing model directory raises `FileNotFoundError` **before** transformers is contacted, and `get_torch_status()["last_load_error"]` records it — verified no repository resolution/download is attempted for a bad path.
- Real Qwen inference succeeded with the offline env vars set (model loaded from `models/qwen/`, generated text).
- Redis is not required (APScheduler in-process fallback).
- Full browser-based end-to-end with the network physically disconnected could not be executed here (no facility to disable the machine's network/firewall mid-session), but every code path, env var, endpoint and model load was verified offline, and real Qwen generation completed without network.
